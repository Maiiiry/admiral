## R65 Multi-Node partition and recovery evidence

On the AlmaLinux 10.2 three-guest topology, an isolated WireGuard overlay partition blocked W2 from reaching the hub. `effective_availability` changed to `unavailable` while the retained last health observation stayed `running/healthy`; the node became `offline/degraded` after about 112 seconds. W1 remained active. After restoring the runtime peer route, W2 returned to active/healthy and the instance to running/healthy/available; direct SQL retained `before-partition`, the app returned HTTP 200, and deprovision cleanup succeeded. No task was in flight, so task-side-effect replay and callback recovery were not covered. The first firewalld setup attempt failed to block traffic and is excluded from the scenario result. Full evidence and limits are in [`release65-alma-multinode-progress.md`](evidence/release65-alma-multinode-progress.md).

## Recovery guarantees visible in implementation

The queue stores durable work in PostgreSQL, claims with a lease, retries with bounded attempts/backoff, and can dead-letter after exhausting attempts. Fleet uses a local outbox for callbacks it could not deliver, and its agent performs health/reconciliation functions. The main control plane and database are not replicated in the supported topology. These mechanisms suggest recovery paths but do not prove safe behavior at every side-effect boundary. At-least-once delivery is the correct assumption.

## Observed worker outage and recovery

The hub marked a suspended worker offline 145 seconds after the VM pause (2-minute heartbeat threshold plus monitor polling). It set node health to degraded and disabled provisioning. The worker's instance still showed `running/healthy` with a pre-outage health timestamp; see `ADM-F-002`. After VM resume, the rootless app, database and infra containers remained `Up`; the node returned to active/healthy after 59 seconds. A separate Rocky Linux 10 test dropped worker1 packets at the hub's underlay ingress: the node became offline after 133 seconds, the assigned instance again remained `running/healthy` with a stale timestamp, and the node rejoined ten seconds after rule removal. The audit did not interrupt an in-flight task or callback and did not test latency. No workload migration occurred.

The AlmaLinux Single-Node guest reboot returned after approximately 28 seconds. System services and workloads came back and database marker `42` survived. Instance state briefly showed `stopped` while Podman containers were already running, then converged within about 36 seconds. A separate `SIGKILL` of the app container was recovered by the generated systemd unit (`Restart=always`) within 3 seconds. The CentOS Stream Single-Node guest also rebooted with a SQL marker in its PostgreSQL volume. The first post-boot probe found only the pod infra container and API state `stopped`; the workload containers later returned, the marker persisted, and the API reached `running/healthy` 91 seconds after the stopped report. A separate deterministic service-failure probe showed that the healthy pod-level signal can hide a failed declared database service (`ADM-F-006`).

## Current conclusion

Real evidence now exists for Single-Node reboot and process recovery plus Multi-Node worker loss/rejoin, local database backup/restore, a controlled packet partition, failed-service injection, Podman deletion failure, and a central database outage. The central database outage failed: R65 valid Fleet workers were IP-blocked after PostgreSQL recovered (HIGH #264), which invalidates R65. The partition exposed stale instance health (`ADM-F-002`). Failed-service injections on CentOS Stream Single-Node and Multi-Node and AlmaLinux Multi-Node exposed successful/healthy reporting while a declared database unit was failed (`ADM-F-006`). AlmaLinux deprovision returned success while an exited infra container, pod and database volume remained after targeted deletion errors (`ADM-F-008`); manual cleanup was required. Rocky, Fedora, AlmaLinux and CentOS Stream hubs started without loading durable WireGuard peer fragments (`ADM-F-005`); manual reconstruction restored the lab clusters. Rocky and Fedora worker reboots preserved SQL markers. AlmaLinux and CentOS Stream local PostgreSQL backup/restore scenarios recovered their original markers. Admirald/Fleet process termination during task side effects, Podman/systemd daemon failure, network latency, memory/disk exhaustion, and interrupted deploy/callback remain NOT TESTED. R65 resilience results are diagnostics only; Single-Node and Multi-Node remain **NOT VALIDATED** until exact-candidate evidence exists.
