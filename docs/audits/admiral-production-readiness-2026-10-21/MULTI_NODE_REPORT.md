## Observed architecture and guarantees

The deployed model is one control-plane hub plus N worker spokes, not a replicated cluster. SSH/Ansible bootstraps nodes; WireGuard carries internal traffic. `admirald` and central PostgreSQL own global state. Workers execute signed, leased tasks through Fleet and report authenticated callbacks. Node health monitoring marks worker nodes offline after a 2-minute heartbeat threshold (observed transition can take up to the threshold plus the 30-second monitor tick). The hub and database remain single points of failure.

The durable queue uses lease-based at-least-once delivery. No exactly-once guarantee was found. A disconnected worker does not receive current tasks or report results. There is no quorum, multi-hub failover, automatic workload migration, or automatic recovery on a replacement worker. A workload remains assigned to its original worker until an operator performs a separately audited action.

## Historical Release 42 execution — AlmaLinux 10.2 x86_64

An isolated three-VM topology used one `--admin-portal-node` hub and two `--worker-node` VMs, each 2 vCPU/2 GiB RAM. Secure install helpers completed on both workers with exit 0, no unreachable hosts and no failed Ansible tasks. The hub listed its portal plus both workers as `active/healthy`; both WireGuard peers had recent handshakes. Fleet was active on each worker and correctly inactive on the hub.

Two explicit provisions ran through the control plane. Instance `inst_51475b49fa4b9b7f` was assigned to worker1 and `inst_ca49a728cc4b0758` to worker2. Both API records reported `running/healthy`, and direct rootless Podman inspection on each worker showed the corresponding infra, app and PostgreSQL containers `Up`. Per-instance Quadlet files, user systemd services, `admiral-apps` lingering and persistent DB volumes were present. Exact sanitized evidence, helper-log hashes and outage timeline are in `evidence/alma-multi-execution.md`.

The worker1 VM was suspended at `13:20:32Z`. At `13:22:57Z` (145 seconds later), Admirald logged the worker offline and exposed `offline/degraded`, `available_for_provisioning=false`, reason `heartbeat_timeout`. The instance itself still reported `running/healthy`, with a `last_health_checked_at` from before the failure. This stale effective state is finding `ADM-F-002`. No automatic migration occurred, as expected from the implementation. After resuming at `13:23:42Z`, the worker's three containers were still `Up`; a heartbeat returned at `13:24:41Z` and the node became `active/healthy/available` again. No duplicate instance IDs appeared.

The worker was then rebooted with `virsh reboot` at `13:33:22Z`. Its boot ID changed; after a short SSH refusal during boot, the same Quadlet-managed containers returned `Up`, PostgreSQL `pg_isready` succeeded, and a fresh heartbeat (`13:34:10Z`) showed `active/healthy/available`. The named DB volume remained mounted at the expected data path. No SQL marker was checked across this worker reboot, so this proves service/volume reattachment rather than application-data integrity.

### AlmaLinux 10.2 x86_64 hub power-cycle and PostgreSQL restore

After starting the previously shut down AlmaLinux hub and two workers, the hub's `wg-quick@wg-admiral` unit was active but both the main config and runtime interface contained zero peers while two durable peer fragments remained. The existing worker workloads came back `Up`, but the API marked both nodes `offline/degraded` and unavailable. This independently reproduces HIGH `ADM-F-005` / #211 on AlmaLinux, the fourth x86_64 target. Manual, lab-only reconstruction from the peer fragments restored two handshakes; by `17:06:25Z`, both workers were active/healthy with their original instance identities. The restricted log hashes and recovery steps are in `evidence/alma-multi-execution.md`.

The follow-up provisioned a disposable `e2e-backup` instance on worker2 and ran a local PostgreSQL backup/restore scenario. A SQL marker was changed after backup; restore while running returned HTTP 409, pause/restore/resume succeeded with checksum verification, and direct SQL returned the original marker. The instance and archive were removed, the instance record is deprovisioned and the backup is marked deleted. This is evidence for local database backup/restore only; S3, volume, Harbor-upload and task-interruption restore scenarios remain untested.

A separate controlled `/bin/false` database-service injection on AlmaLinux worker2 reproduced HIGH `ADM-F-006` / #227: provision operation `op_fe3466ba3ea600f1` succeeded, the DB systemd unit failed with exit status 1 and five restarts, and the DB container was absent while the app/pod remained up and the API continued to report `running/healthy` for more than three minutes. Deprovision `op_e31b2d55a055d57e` succeeded; Podman, Quadlet, instance-directory and user-unit checks were empty. Raw evidence hash and the sampling caveats are in `evidence/alma-multi-execution.md`.

A subsequent AlmaLinux deprovision fault injection reproduced HIGH `ADM-F-008` / #228. Nine Podman deletion calls for one disposable instance were made to fail while all unrelated Podman calls continued normally. Deprovision returned `succeeded`, but an exited infra container, pod and PostgreSQL volume remained; the Quadlet files and instance data directory were already gone, and the API still showed `stopped`. The original Podman binary was restored byte-identically and manual cleanup left zero matching resources. No other worker2 workloads were affected; details and restricted raw-log hash are in `evidence/alma-multi-execution.md`.

The candidate Go binaries report Go `1.26.7`. `govulncheck` found 10 reachable standard-library advisories in Fleet/CLI and 11 in Admirald, including an HTTP/2 server crash advisory. From an enrolled worker, an unauthenticated HTTP/2 request to the hub's WireGuard-bound Admirald listener negotiated HTTP/2 and received 401 after reaching the application. The exploit frame sequence was not sent. This reachable denial-of-service exposure is HIGH finding `ADM-F-003` and blocks Multi-Node readiness.

### Rocky Linux 10 x86_64 hub power-cycle and recovery

The three existing Release 42 Rocky guests were powered off and started from disk. On hub startup, WireGuard came up without peers: the main config had zero peer sections and the runtime interface had zero peers, while two durable peer fragments remained under `/etc/wireguard/peers.d/`. The hub marked both workers offline/degraded; their Fleet task-claim and heartbeat calls timed out. This is a real recovery failure, `ADM-F-005` (HIGH). The outage occurred with no active app workload, so data integrity during an assigned workload outage was not tested.

The test manually reconstructed the hub's main WireGuard config from the fragments and restarted the service. Both peers handshook and all nodes returned to active/healthy; by `14:09:31Z` workers were again available. The worker onboarding role writes live peers and durable fragments, while the `wg-quick@` boot unit reads only the main config. This manual recovery allowed testing to continue but does not count as automatic recovery.

With the lab network restored, `e2e-whoami` was explicitly provisioned on each Rocky worker. Both operations succeeded, the hub showed each instance running/healthy on its requested node, and each worker's rootless Podman showed its infra, app and database containers running. Operation IDs, timestamps, restart and persistence results are in `evidence/rocky-multi-placement.md`; the restricted raw console log remains ignored and mode 0600.

### Rocky Linux 10 x86_64 controlled worker partition

After successful placement of a disposable `e2e-whoami` workload on Rocky worker1, an isolated nftables rule on the hub dropped packets arriving on `enp2s0` from `10.77.0.11`. The rule began at `14:23:27Z`; the worker remained reported active until `14:25:29Z` and was marked `offline/degraded`, unavailable for provisioning, at `14:25:40Z` (133 seconds after the drop). At that same time, the instance API still reported `technical_status=running` and `health_status=healthy`, with `last_health_checked_at=14:22:58.727Z`, before the test started. This reproduces `ADM-F-002` under a true packet filter as well as under VM suspension.

Removing the nftables table at `14:25:40Z` restored `active/healthy/available` by `14:25:50Z`. The instance retained its ID and running/healthy status. No task was in flight, so lease/callback retry semantics were not exercised. Explicit deprovision succeeded; direct worker inspection showed zero rootless containers, zero Podman volumes and zero matching instance Quadlet files. Full timestamps, the reproduction command and raw-log hashes are recorded in `evidence/rocky-multi-partition.md`.

This provides three-node integration, a whole-VM outage/rejoin test, a worker guest reboot test and a real controlled network partition. It does not establish safe task-side-effect recovery or automatic migration.

### Fedora Rawhide x86_64 hub restart, placement and worker reboot

The three existing Fedora Rawhide guests started with a hub configuration containing zero peer sections and zero runtime peers despite two mode-0600 peer fragments. Both workers were `offline/degraded`, with last heartbeats from `02:06Z`, and Fleet logged task-claim timeouts. This independently reproduced `ADM-F-005` on the second target OS. As on Rocky, the lab hub was manually reconstructed from the durable fragments and restarted; two fresh handshakes appeared and the workers returned to `active/healthy` within five seconds. The workaround changed only the isolated guest configuration.

After recovery, `e2e-whoami` provisioning succeeded on both workers and direct rootless Podman inspection confirmed the app, infrastructure and database containers. PostgreSQL accepted connections. A SQL marker on worker2 survived a guest reboot: the boot ID changed and SSH returned in about 35 seconds, then the same containers returned and PostgreSQL accepted connections. Both instances were successfully deprovisioned, each worker had zero test containers, volumes and Quadlet files, and the hub retained all nodes as active/healthy. Full operation IDs, intervals and raw-log hashes are in `evidence/fedora-multi-hub-reboot.md`.

## Operational limits

Loss of the hub or central database blocks new control-plane operations and callbacks. Workers may keep already-running local workloads under systemd, but the hub cannot authoritatively coordinate them while disconnected. A worker loss interrupts only workloads placed there; this audit observed no automatic rescheduling. The offline detector makes the node unavailable after a bounded heartbeat timeout, but instance-level health remains last-known during the outage; AlmaLinux, Rocky Linux and CentOS Stream runtime tests reproduce `ADM-F-002` / #208. R65 additionally reproduced HIGH #264: central PostgreSQL unavailability caused valid worker tokens to exhaust the auth limiter and be IP-blocked after recovery; the exact R66 AlmaLinux three-guest regression passed for 503/Retry-After, zero 401/429 and worker recovery, with #264 left open for broader matrix review. CentOS Stream Single-Node/Multi-Node and AlmaLinux Multi-Node `/bin/false` injections confirmed that Fleet reports healthy while a declared service is failed (`ADM-F-006`). AlmaLinux Multi-Node also reported deprovision success after Podman deletion errors left an exited infra container, pod and DB volume (`ADM-F-008`). Production configuration accepts placeholder encryption/callback keys that would affect any topology retaining the shipped defaults (`ADM-F-007`). Hub restart lost WireGuard runtime peers on Rocky, Fedora, AlmaLinux and CentOS Stream despite durable peer fragments and required manual config reconstruction (`ADM-F-005`). Local PostgreSQL workload backup/restore passed on both AlmaLinux and CentOS Stream; S3/volume restore and WireGuard identity backup/recovery need separate clean-guest drills.
