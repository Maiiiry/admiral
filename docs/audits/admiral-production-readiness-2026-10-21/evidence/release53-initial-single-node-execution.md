# Release 53 initial Single-Node runtime execution

Audit: `ADM-AUDIT-2026-10-21`
Candidate: RC5 Release 53 x86_64 RPMs, package-preparation commit [`e149571`](https://github.com/admiral-project/admiral/commit/e149571e6124d1e4223f2c868a2a1c1f685f8d58). Exact source refs, NEVRAs and package hashes: [`release53-candidate.md`](release53-candidate.md).
Disposition: **Fedora and Rocky passed multiple named Single-Node scenarios, including a verified guest reboot with workload and SQL-marker recovery; no complete matrix cell has passed. Matrix remains 0/8.** These are candidate-specific scenario results, not production-readiness decisions.

## Lab and package identity

Two fresh 2-vCPU / 2-GiB x86_64 libvirt overlays were created from the updated 2026-10-22 Fedora Rawhide and Rocky Linux 10.2 seeds. Host: Rocky Linux 10.2, 4 vCPU, 8 GiB RAM plus 4 GiB swap, KVM, SELinux enforcing. Both guests reported SELinux enforcing after setup. The RPM repository served Release 53; the installer verified all six exact `0.0.1rc5-53.el10` NEVRAs. The build and repo metadata hashes are in the candidate record.

The six exact packages and the principal Admiral systemd services were present and active in both post-install baselines. Rootless Podman reported `true`. The initial seed-based package check reported `Nothing to do`; install transactions added Admiral's declared runtime and security-policy packages. No full OS update command was run for these candidate VMs. The Fedora installer output included repeated HTTP 403 responses from the optional OpenH264 repository; DNF continued with Fedora, COPR and local candidate repositories, and the installer completed. During initial registration, the installer retried the local worker heartbeat 23 times on Fedora and 24 on Rocky before both completed with no failed Ansible tasks.

### DHCP address mismatch during VM preparation

The create helper requested `.252` for Fedora and `.253` for Rocky, but stale leases from removed Release 52 guests still held those addresses for their previous MACs. The new guests first received `.233` and `.232`. Strict SSH to the requested addresses failed with `No route to host`; strict host-key verification remained enabled. At 07:33 UTC, after the old leases expired, dnsmasq moved the new MACs to `.252` and `.253` without guest reconfiguration. We confirmed each lease by MAC and matched the guest host key to the host-generated key before connecting. The failed SSH attempts occurred before RPM transfer or installation. This harness defect is tracked in open issue [#247](https://github.com/admiral-project/admiral/issues/247), linked to master tracker [#200](https://github.com/admiral-project/admiral/issues/200). The new helper regression detects and rejects a mismatched lease before reporting a guest ready; #247 has `fix-proposed` pending root CI. This does not alter or invalidate the Admiral RPM candidate.

## Scope and remaining work

This execution confirms multiple named R53 Single-Node scenarios on Fedora and Rocky, including #246 secret-preservation, same-key idempotency, local DB backup/restore, declared-service failure detection, selected namespace/privilege checks, process recovery, and host reboot recovery. Issue #246 remains open pending complete release validation and Multi-Node regression. The Fedora health state lag after Reactivate was observed accurately as unavailable before a fresh healthy report arrived; this did not become false `healthy` state and the SQL marker remained readable afterward. No new Admiral defect was confirmed by this delay.

These scenario results still do not complete either OS cell. Fedora and Rocky Single-Node still need complete lifecycle/update/delete coverage, broader concurrency and idempotency retries, cross-workload network/storage/secret negatives, Podman/systemd daemon failures, controlled resource pressure, measured performance, and clean dependency installation proof from intended repositories. The targeted R53 host reboot and SQL-marker check passed on both, but it does not complete the wider resilience catalog. AlmaLinux and CentOS Stream R53 follow-up results are in [`release53-followup-single-node-execution.md`](release53-followup-single-node-execution.md). No R53 Multi-Node topology has run. The active matrix remains **0/8**, all eight full cells are incomplete, and both production readiness decisions remain **NOT VALIDATED**. Issues #247 and #248 have fixes on root main with green CI; #249 records the local runbook correction. All remain open; no issue was closed.
