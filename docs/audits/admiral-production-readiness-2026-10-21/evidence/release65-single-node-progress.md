## Security and isolation limits

On each OS, two simultaneous test workloads used different database secrets and volume sources, separate PID and network namespaces, no privileged mode, no Podman socket mount, and `no-new-privileges`. A connection from workload A to workload B's host-mapped application port was refused. The probe from A directly to B's PostgreSQL container IP is **NOT TESTED**: rootless Podman did not expose a target container IP to this probe. Therefore these observations are partial isolation evidence, not a claim that cross-workload database reachability has been disproved.

The cgroup probes found the tier limits on the effective systemd ancestor slice (small: 512 MiB and 1 CPU; medium: 768 MiB and 1 CPU). Podman inspect on the individual containers reports zero direct memory/CPU limits; the test counts the effective ancestor enforcement and records that runtime representation. Negative API probes without credentials and with invalid tokens returned HTTP 401. These selected checks do not replace a full security review.

## Reproduction and interpretation

Run the R65 shell probes under `scripts/r65/` only on fresh disposable guests with the exact R65 packages. The single-node bootstrap is `scripts/install-single-node-audit.sh`; workload fixtures are in `fixtures/`. Probe logs include UTC timestamps and operation IDs. The CI build and DNF resolution are package evidence; the VM scenarios are end-to-end/runtime evidence. Do not mark any unexecuted scenario PASS. A candidate-affecting defect discovered after this evidence would invalidate the affected candidate results and require a rebuilt release and rerun.

No new product defect was confirmed in these R65 named probes. No issue was closed. Multi-Node, sustained stress/performance, OOM/disk exhaustion, network partition/latency, external object-store restore, and direct cross-workload PostgreSQL-IP isolation remain untested.
