# Lab harness events and preserved failures

These events are lab-preparation defects, not Admiral product results. They are retained because failed attempts are part of the audit trail.

1. Initial AlmaLinux/CentOS seed cloud-init run: `write_files` assigned `/home/validator/validator.pub` to `validator:validator` before cloud-init created the user, so the network stage logged “Unknown user or group: validator” and cloud-init ended in error. The guest user/SSH setup otherwise completed. The old raw diagnostics are retained in the ignored `packaging/build/validation/rc5-r42/*seed-cloud-init-failure.log` files; they were not copied here because the automated content scan found secret-related markers requiring manual review. The VM helper was corrected to write a root-owned temporary public-key file and install it to the validator home from `runcmd`, after user creation. A fresh AlmaLinux audit guest then reported cloud-init `done`, systemd `running`, AlmaLinux 10.2, SELinux `Enforcing`, kernel `6.12.0-211.66.1.el10_2.x86_64`, and the expected public-key file owner/mode. See `alma-single-cloud-init.txt`.
2. First call to the newly created single-node install wrapper returned `sudo: admiral-install: command not found`. The guest had not yet installed `admiral-common`, which provides that command. This exposed a missing bootstrap step in the audit helper, not a product failure. The helper was changed to enable EPEL, CRB and Admiral COPR, install the exact six local candidate RPMs, and then invoke the packaged installer. The corrected first run completed its Ansible play and printed completion with zero failed tasks, but the outer SSH wrapper returned exit 127 without an end timestamp. A repeated install returned 0. The first-run wrapper discrepancy remains unresolved; outcomes are recorded without upgrading it to a clean wrapper PASS. See `evidence/alma-single-execution.md` and the ignored mode-0600 raw log `packaging/build/validation/rc5-r42/audit-alma-single-install.log`.
3. First host-preflight script invocation returned `qemu-kvm: command not found`; this host exposes the QEMU version through libvirt/RPM metadata rather than that executable name. The preflight helper now checks `qemu-system-x86_64`, `/usr/libexec/qemu-kvm`, then RPM metadata. The rerun completed and is recorded in `lab-preflight.txt`.

4. The first direct single-node CLI backup attempt used an application tier with manual backups disabled and correctly returned HTTP 403. A dedicated audit fixture enabling database backup was then used; the backup/restore marker test completed successfully. This is an expected policy rejection, not a product failure.
5. The first attempt to validate remote worker containers with the bootstrap SSH key was rejected after worker setup. The installer had revoked that bootstrap key and created per-node `admiral-ssh` delivery identities. The audit then used those identities, with pinned host fingerprints, to inspect worker-local Podman state. This is expected hardening behavior.

None of these harness or expected-policy outcomes was removed or recast as an unqualified product PASS. Raw cloud-init and install logs remain ignored local files with restricted modes; tracked evidence contains only sanitized results and this event record.
